# review-comments

コメントは何を書いているかではなく、コードから読み取れない情報を補っているかどうかで要否を判断する。

## 前提

- コメントには、インターフェースの契約 (呼び出し側が知るべき前提条件、不変条件、エラー)、Why not、コードから読み取れない制約を書く。処理手順をなぞるだけのコメントは書かない。
- コメントで補わないと分からないコードは、コメントを足すのではなく名前や抽象の境界を見直す。

## 対象範囲

引数でファイル・ディレクトリ・コミット範囲が指定されたらそれに従う。指定がなければ、作業ツリーの未コミット差分にあるファイルを対象にする。

```bash
git diff --no-ext-diff --name-only
```

`diff.external` に difftastic が設定されているため、`--no-ext-diff` を忘れると出力が壊れる。

## 判定基準

対象範囲にあるコメントを 1 つずつ次の順で判定する。

1. インターフェースの契約を書いたコメントか → 呼び出し側が実装を読まずに正しく使えるようにしているなら保持
2. コメントを消してもコードから同じ情報が読み取れるか → 読み取れるなら削除
3. なぜこの実装にしたかの理由 (why not) は、その言語・フレームワークの一般的なイディオムで推測できるか → 推測できるなら削除。プロジェクト固有の制約、非自明な不変条件、特定の不具合の回避策、外部システムの癖など、そのイディオムを知っていても気づけない理由を説明している場合のみ保持
4. TODO・FIXME・HACK か → 対応方針や参照先が明確なら保持、曖昧ならユーザーに要否を確認
5. コメントアウトされたコードか → 削除。過去の実装は git 履歴で追える
6. 処理手順の説明のみか → 削除。ただし本来インターフェースの契約や why not を書くべき箇所であれば、削除ではなくその内容に書き換える。説明がないと分からないコードであれば、名前や抽象の境界の見直しを提案する

## 手順

1. 対象範囲のコメントを列挙する
2. 各コメントを上記基準で判定し、削除・保持・書き換えの一覧を判定理由付きで提示する
3. このセッションで Claude が追加・変更したコメントは、確認を待たずに Edit で反映し、一覧を報告に含める。それ以外のコメントは、一覧をユーザーに確認してもらってから反映する
4. 名前や抽象の境界の見直しが必要と判断したものは、見直し案も合わせて提示する

## 注意

- コメントの要否だけを見る。ロジックの妥当性やスタイルには踏み込まない。
- 判定理由を省略して一括で消さない。保持と判定したコメントも、なぜ保持したかを一覧に含める。
