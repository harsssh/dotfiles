# write-tests

テストは仕様 (What) を表現する。実装をなぞるのではなく、仕様から導いたケースの一覧をテストに写す。

## 手順

1. 対象の仕様を確認する。仕様書・issue・既存のテスト・呼び出し元から読み取れない点は、推測で埋めずにユーザーに確認する
2. 仕様からテストケースを列挙し、一覧としてユーザーに提示する
3. 一覧と 1 対 1 に対応するテストを書く
4. テストを実行し、結果をそのまま報告する

## テストケースの列挙

次の観点で列挙する。

- 正常系の入力の分類: 入力を、期待する結果が変わる単位で分ける
- 境界値: 分類の境目の値と、その前後の値
- エラー・失敗のケース: 不正な入力、依存先の失敗、失敗を表す戻り値
- 状態ごとの振る舞い: 対象が状態を持つなら、状態ごとに同じ操作の結果を確認する

次のものは列挙しない。

- 型で保証されていること
- 他のテストで検証済みのこと
- 実装の詳細 (内部の呼び出し順、private なメソッドの挙動など)

一覧の各項目は「入力条件 → 期待する結果」の形で書く。この文はそのままテスト名になる。

## テストの書き方

- 一覧にないテストを書かない。一覧にあるケースを漏らさない。書いている途中でケースの追加が必要だと気づいたら、一覧を更新して提示し直す
- 1 つのテストで検証する事柄は 1 つにする
- テスト名は英語で、入力条件と期待する結果で書く。RSpec の describe / context / it の文字列なども同じ
- 純粋関数は直接テストする。副作用を持つ関数のテストは、モックを使って純粋関数との接続だけを確認する最小限にとどめる
- テストデータや期待値がドメイン概念・既存データに紐づくなら、その定数・変数を参照する式で書く
- 期待値を実装と同じロジックで計算しない。具体的な値で書く

## 実行と報告

- 失敗したテストは、失敗の出力をそのまま報告する
- テストを通すために期待値を書き換えたり、skip したりしない。期待値が誤っていると判断した場合は、その理由を示してユーザーに確認する
