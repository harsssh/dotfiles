# CLAUDE.md ユーザー設定

## 全般

- 日本語で回答する
- コードコメントは日本語、テスト名は英語で書く

## 文章

- 記号は全角ではなく半角を使う
- 記号、英字の周りに 1 つスペースを入れる
- 太字や斜体などの装飾はしない。ただし、見出しや箇条書きなど文構造を表現する記法は使ってよい
- 順序に意味がない列挙は順序リストではなく箇条書きを使う
- 調査結果を報告するときは、最後にまとめを書く
- 造語は使わない。日本語として一般的な表現、技術的に正しい表現を使う。英語での呼称を直訳したものも、日本語で一般的に使われるものではないなら禁止

## コーディング

### 設計・品質

- 何をどう処理するか (How) はコードで表現し、コメントには書かない。コードコメントには、そう書かなかった理由 (Why not) や、コードから読み取れない制約だけを書く
- テストコードは仕様 (What) を表現する。コミットログには変更の理由 (Why) を書く
- 関数の処理内容を説明するだけのコメントは書いてはいけない。説明が必要なほど長い関数は分割を検討する
- Tell-Don't-Ask: オブジェクトの状態を取り出して呼び出し側で分岐せず、その分岐をオブジェクトのメソッドにする
- 同じロジックを複数レイヤに置かない
- formatter, linter のエラーを ignore コメントで無効化してはいけない

### 関数型スタイル

- 関数は純粋関数と副作用を持つ関数に分ける。1 つの関数に両方を混ぜない
  - 副作用とは、IO (ファイル、ネットワーク、DB)、現在時刻の取得、乱数生成、引数以外の状態の読み書きのこと
  - 判断や変換のロジックは純粋関数に書く。副作用を持つ関数は、副作用の実行と純粋関数の呼び出しだけを行う
  - 純粋関数はモックなしで単体テストできること
- 値は immutable にする。変更が必要なら新しい値を作って返す
- 状態や不変条件は型で表現する
  - 状態が異なれば別の型にする (例: 未検証の入力と検証済みの値)
  - 取りうる値が有限なら bool や string ではなく列挙型にする
  - 失敗しうる関数は、失敗することが戻り値の型から分かるようにする
- 上記はその言語の標準的な手段で実現する。Maybe や Either のような他言語の構造を模倣したクラスやライブラリを導入しない

### 命名

- 述語は肯定形で命名
- 仕様書の語彙をコードに反映する。独自の語を作らず、仕様・コード・テスト・API で同じ概念を同じ語で呼ぶ
- 英文法的に自然な識別子を選ぶ

### テスト

- 振る舞いを変える変更には、テストを追加または更新する
- テストを書く前に、仕様からテストケースを列挙し、一覧として提示する。列挙の観点は、正常系の入力の分類、境界値、エラー・失敗のケース、状態ごとの振る舞い
  - テストはこの一覧と 1 対 1 に対応させる。一覧にないテストを書かず、一覧にあるケースを漏らさない
  - 型で保証されていること、他のテストで検証済みのこと、実装の詳細 (内部の呼び出し順など) はテストしない
- 1 つのテストで検証する事柄は 1 つにする。テスト名は入力条件と期待する結果で書く (RSpec の describe / context / it の文字列なども含む)
- 純粋関数は直接テストする。副作用を持つ関数のテストは、モックを使って純粋関数との接続だけを確認する最小限にとどめる
- テストデータや期待値がドメイン概念・既存データに紐づくなら、その定数・変数を参照する式で書く
- 期待値を実装と同じロジックで計算しない。具体的な値で書く
- 変更後はテストを実行し、結果をそのまま報告する。テストを通すために期待値の書き換えや skip をしない

## 言語・ツール別

### シェル

- alias で `rm` は interactive に実行されるので、ファイルを削除するときは `rm -f` を使う

### git, gh

- ブランチの切り替えは git-switch、ファイルの復元は git-restore を使う。git-checkout, git-reset は使わない
- 未コミットの変更を破棄する操作 (`git restore .`、`git reset --hard`、`git clean` など) はユーザーの指示があるときだけ行う
- ユーザーの指示なく PR を作成してはいけない
- ブランチ名は kebab-case を使う。日付などは含めない

### Nix

- 作業が完了したら `nix flake check` で検証する
- 再現性を最重視して設定を書く
- warning は解消する。解消できない warning はその理由を報告する

### Ruby

- 3.1+ の hash shorthand を活用する
- 重複する setup は shared_examples / shared_context に括り出す
